# Architecture

The decisions made so far and how the application is built. What is planned is in the [roadmap](roadmap.md).

## Decisions

| Topic | Decision | Rationale |
|---|---|---|
| Backend | Go, modular monolith, single binary | Low memory use, simple deployment, `x/net/webdav` for WebDAV uploads |
| Frontend | Vue 3, Vuetify, Vite, Pinia | Project requirement. The virtual-scrolling timeline grid is custom, as Vuetify has no such component |
| Look | PatternFly 6, built on Vuetify: its tokens go into the Vuetify themes, component defaults and one stylesheet. Fuchsia replaces the PatternFly blue. Red Hat fonts, with Inter for Cyrillic, which they lack. Font Awesome Free icons, bundled one SVG at a time. A menu in the app bar chooses the color scheme and the contrast mode (default, high contrast, glass), kept in the browser | A clear, consistent design system without rewriting the frontend: PatternFly has no Vue components. A theme belongs to the device, as a phone and a laptop can sit in different light |
| Database | PostgreSQL | Relations and permissions, JSONB for EXIF, search, `pgvector` for photo embeddings. Keep it on an SSD if the NAS has one |
| Job queue | River (on PostgreSQL), no Redis | A photo and its job are written in one transaction, and there is one service less to run. No official BullMQ client for Go was found |
| API | REST with OpenAPI, SSE for progress | Works well with browsers, files and caching. A monolith needs no internal RPC. The ML service is called over HTTP too: its requests are few and large, so gRPC would gain nothing |
| Image processing | libvips through govips | libvips is fast and memory-efficient. govips has a long history, a large community, and is not tied to one libvips version |
| Photo metadata | exiftool through go-exiftool | Handles HEIC and camera-specific tags. One long-running process avoids starting Perl for every photo |
| Folder scan | Copy files into the library, leave the source folder untouched | One ingest path for all sources |
| What a scan covers | A folder inside a fixed root, chosen by the administrator, with an owner for the scan. One scan at a time | Folders per user can be imported to their owners. Nothing outside the root is reachable |
| Running a scan | A River job on its own queue with one worker. It records the list of files in the database, then works through it in slices | A scan can take hours, and continues after a restart with correct counts. It takes no worker from photo processing |
| Permanently deleted photos | The row stays with its hash, stripped of everything else, and files are removed. A scan leaves such a photo out, and an upload adds it again as a new photo | Adding files to a folder and scanning it again must not bring back what the owner deleted, or fill the disk again |
| Sharing | Photos and albums, with all users or by login | Sharing an album makes all of its photos visible to the recipient |
| Rights of a recipient | View and download, read-only | A recipient cannot change, tag or pass on another user's photo, or add it to an album. Tags and albums of shared photos can be reconsidered later |
| Timeline contents | The user's photos and, by default, every processed photo of other users that the user can see, including the photos of shared albums. A "Mine / All" switch above the timeline changes this and is saved for the user. Only the user's own photos can be selected, and others open read-only in the viewer. The camera and lens filters cover all of them. A tag filter finds only the user's own photos, as tags are personal. An administrator's timeline follows the same rule, and all users' photos stay on the administrator's page | A user who had uploaded nothing saw an empty start page, even with photos shared with them. The switch sits on the page rather than in the profile, because one large shared album can push the user's own photos aside |
| "Shared with me" | Albums and photos tabs. Each user chooses whether the photos tab includes the photos of shared albums, which is off by default | One large album would otherwise push everything else out of the list |
| Choosing a recipient | Autocomplete from the logins of active users, available to every logged-in user | Convenient and free of typos. On a home NAS, users knowing each other's logins is not a concern |
| Viewer source | The viewer preview. Each user can choose in the profile to load the original when zooming in, which is off by default; otherwise zooming enlarges the preview. An original the browser cannot decode, such as HEIC outside Safari, falls back to the preview | Originals can be many times larger than previews, which matters on a phone or a slow connection. Only zooming needs more than a preview has |
| Photo details in the viewer | Each user chooses in the profile which camera details and whether the location the viewer shows. All are shown by default. The interface hides them, and the API still returns them | A display preference, not a privacy setting: whether locations are returned at all stays with the administrator |
| Zooming in the viewer | A photo larger than the screen zooms with a click, the wheel or a pinch to the resolution of its original when the user chose in the profile to load originals for zooming and the browser can decode it, and otherwise to the resolution of the viewer preview, past which the photo would only blur. A pinch scales with the distance between the fingers and keeps the point between them in place. The viewer handles the gestures itself, without a library | `@panzoom/panzoom` was used first. Its pinch zoomed linearly with the finger distance, too slowly for large photos, and its zoom point assumed a photo in the corner of its container, so a centred photo zoomed in the wrong place or off the screen |
| Timeline loading | Lists sorted by date load month by month. The server first counts the photos of each month in the browser's time zone. The grid lays out every month from these counts and loads the photos of the months near the screen, at most three at a time. The trash, sorted by deletion time, loads page by page as it scrolls | The scroll bar covers the whole library, and any year is reachable without loading everything newer first |
| Timeline navigation | Month titles in the grid and a scrubber with the years on the right. On a touch screen the scrubber shows while the list scrolls; with a mouse it stays | The right edge is where the thumb is and where phones put such a scrubber |
| Grid tiles | Rows that keep each photo's shape by default. Each user can switch to squares in the profile, and choose a size of small, medium (the default) or large for both. On a grid 600 CSS pixels wide or more the sizes aim at 150, 200 and 280 pixels: the height of a row and the side of a square. On a narrower grid they give 4, 3 and 2 squares in a row, and rows aim at the side of those squares. A square is a little larger or smaller so that whole squares fill a row. A row ends before or after the photo that overflows it, whichever brings its height closer to the target, and grows at most 1.4 times the target | The same size on any screen density, so tiles are not smaller on a denser screen. Three levels rather than a slider: the largest tile, about 400 pixels, stays within what the largest grid preview (800) covers on a 2× screen, so no size looks blurry. On a screen denser than the grid preview size allows, the preview is scaled up a little; a larger grid preview size keeps it sharp. The grid preview size is the shortest side, so a square cut from a preview keeps full resolution |
| Menu on a phone | Hidden until the menu button opens it over the page. Each user can keep the permanent rail in the profile instead | The rail takes a sixth of a phone's width |
| Preview settings | Stored in the database and edited on an administration page. They apply to new photos only. The `render-grid` command makes the grid previews of all photos again, from their viewer previews, with the current size and quality, and in the format each photo already has. Purely technical settings, such as the number of workers, stay in the environment | Regenerating all previews takes hours and needs its own progress and safeguards. Grid previews alone are cheap to make from viewer previews, and they are what a change of the grid preview size affects |
| Grid preview size | The shortest side of the preview, never more than the viewer preview has. It sets how sharp grid tiles are, not their size: about 200 × the screen density for medium tiles and 280 × for large ones. A preview's address carries a version that changes when it is made again | Square tiles crop the long side, so the short side must have the full size. A 3:2 grid preview has 1.5 times as many pixels as one limited by the long side. Previews are cached for a year, so without the version a browser would keep the old one |
| Administrator | A page with all users' photos and an owner filter, where the administrator can change sharing and move photos to the trash. Other users' albums are read-only and tags stay hidden. Restoring and permanently deleting stay with the owner | An administrator cannot lose someone's photos by accident |
| Tags | Personal to each user. A search with several tags finds photos with any of them | Other users' tag names stay private |
| Camera and lens filters | The timeline filters its photos by camera and by lens, choosing from those its photos have. Several cameras or several lenses find photos with any of them; different filters must all match. Each list counts its photos with the other filters, including tags and dates, and leaves out names with none, except those already chosen. A camera is named by its make and model, without the make when the model repeats it. A lens is LensModel, or Lens or LensID for older cameras, leaving out numeric codes. PostgreSQL keeps both in generated columns of `photos`, and the viewer shows the same lens | Photos processed before the filters get them without reprocessing, and the filter and the viewer cannot disagree |
| Type filter | The timeline filters by type: still photos, photos with motion (Android motion photos and paired Live Photos) and videos. Each item is exactly one type, so the counts add up to the library, and several types find items of any of them. The list counts each type with the other filters, as the camera list does. The type comes from the stored MIME type and `has_motion` through the SQL function `photo_kind` | Decided with the user on 2026-11-12. Separate types keep a choice of "Photos" from bringing back the motion photos the user meant to leave out. Screenshots, panoramas, slow motion and time-lapses are left for later: screenshots and documents are better told apart by the stage 7 embedding |
| Album covers | The newest processed photo, unless the owner chooses one | Works without effort, and can still be set by hand |
| Trash | Photos stay until the owner restores or permanently deletes them, with no automatic expiry | Nothing is lost by waiting. Emptying the trash is the way to free disk space |
| Uploading a photo that is in the trash | Restores it, with its albums and tags | Uploading it again shows that the owner wants it back |
| WebDAV contents | Each user has a folder tree of their own, kept in the database. A file in it records an upload and points to the photo it became; the file itself is not kept, as the library has the original. A GET returns that original | Sync clients compare the server's listing with the phone to decide what to send. An empty folder would make them send everything again on every sync |
| WebDAV passwords | App passwords, any number per user, named after the device. The server makes a random one, shows it once and stores its SHA-256. Each can be revoked on its own. The account password does not work over WebDAV | Basic Auth sends the password with every request, too often for argon2id, and a random password needs no slow hash. A lost phone is revoked without logging out the others |
| Deleting over WebDAV | Removes the file from the WebDAV tree only. The photo stays in the library | Sync apps delete on the server what is gone from the phone, and clearing space on a phone must not delete its photos here |
| WebDAV and the trash | As with a folder scan: a photo in the trash stays there, and a permanently deleted one is not added again. Files that are neither supported photos nor videos are refused with 415 | A phone that sends its camera roll again gives no sign that the owner wants a deleted photo back |
| WebDAV albums | The owner links a folder of their WebDAV tree to one of their albums in the profile, and photos uploaded into that folder or its subfolders are added to the album. The nearest linked folder decides, so a subfolder can have an album of its own. This includes a photo the library already has, unless it is in the trash. A link names a path: it can be made before a sync app creates the folder, and it stays when the folder is deleted or moved. Folders are linked, not app passwords. Folder names never create albums. Deleting or moving a file over WebDAV leaves the photo in its album | A sync app pairs each phone folder with a server folder, so the camera and a messenger can go to different albums with nothing set up on the phone. Albums made from folder names would fill the list with `DCIM` and `Screenshots`. Removing photos from an album on delete would contradict keeping them in the library. A link per app password would send everything from a phone to one album, or need a password per folder pair |
| Videos | MP4 and MOV go through the same ingest as photos and live in the same table, told apart by the MIME type, so albums, tags, sharing, the trash and search cover them with no code of their own. Processing reads the duration with ffprobe, takes a frame one second in as the poster, tone mapped to SDR when the video is HDR, and makes the previews from it with libvips. The ML service embeds the viewer preview, so videos are found by description too. The viewer plays the original in a `<video>` once the user starts it, and shows the poster with a download when the browser cannot play the codec, such as HEVC in some browsers, unless an H.264 copy is made, as described under Video copies | The original plays with seeking through range requests, with nothing to store twice. A frame is enough for the grid and for search. Starting playback by hand keeps stepping through a library from downloading every video |
| Video copies | With the transcoder, a service next to the application whose image carries the drivers for one maker of graphics, the application makes H.264 copies of HEVC, VP9 and AV1 videos, of HDR videos in H.264 and of the motion of motion photos and Live Photos, the only codecs it copies: H.264 plays everywhere, though Firefox shows an HDR one grey without tone mapping, and ProRes, MPEG-4 Part 2 and MJPEG would need decoding on the CPU. Decoding, scaling to the shorter side at 1080, tone mapping HDR with `tonemap_opencl` and encoding with `h264_vaapi` all run on the graphics, with no CPU fallback. A copy has no metadata tags and keeps the rotation of the original. It lives in the cache next to the previews, and `photos.video_copy` records whether it is ready, not needed or failed; the copy of a Live Photo's motion belongs to the photo. The administration page sets when copies are made: off, after upload (including the videos uploaded before, by a job at every start and once a day), or when someone first plays the item, the default. A job on a queue of its own with one worker makes one copy at a time, and an item someone is waiting for goes first. The viewer always plays the copy once it exists; until then it plays the original where the browser can, and otherwise waits for the copy. An HDR video, which `photos.hdr` marks from processing or from the `backfill_video_hdr` job at every start and once a day, waits for its copy on its first play too, as Firefox plays it grey, and plays the original when no copy is coming or the user chooses it instead of waiting; the motion of photos does not wait. Turning copies off keeps those made. A copy that fails twice is not tried again. The application probes the video, decides on the copy and keeps the queue, and sends the transcoder the paths of the video and of a temporary file in the cache over HTTP with a bearer token; the transcoder sees the library read-only and the cache at the same paths, runs as the same user, and writes the copy. The application asks it for its graphics every 30 seconds; while it is unreachable no copies are queued and none are marked failed, and the items that waited are queued again when it is back. What differs between makers of graphics, how the driver is recognised and how HDR is tone mapped, lives in a file per vendor in `backend/internal/vaapi`. The Intel image tone maps HDR with `tonemap_opencl`; the AMD image, with Mesa's radeonsi driver, makes copies of SDR videos only, until the way to tone map HDR there is measured | Decided with the user on 2026-11-13 after the [benchmark](benchmark.md#video-results): on the N150 `h264_vaapi` is about 20 times faster than libx264 on HDR, and `tonemap_opencl` is the only tone mapping that takes the HLG of an iPhone. Copies on first play spend the graphics and the SSD only on videos someone watches. The drivers and the OpenCL runtime add about 460 MB, and each maker of graphics needs its own, so on 2026-11-14 the user chose a service with an image per vendor over an application image per vendor: the application's image stays the same everywhere, and AMD graphics are supported next to Intel without a second application image. The main image and arm64 without a transcoder keep videos as they are. HDR videos in H.264 were added on 2026-11-19, after a PQ video from the NAS played grey in Firefox |
| Video dates | An iPhone's `CreationDate`, which carries the offset, then QuickTime's `CreateDate`, which is UTC by the standard | `parseDate` already reads a date without an offset as UTC, so exiftool's `QuickTimeUTC` option is not needed. Photo dates stay as they were |
| Photos being processed | The timeline, albums, favorites, the archive, the administrator's view of all photos and their month counts and facets leave out a photo until processing has made it ready; a failed photo shows, with its error. The upload panel and the processing count in the app bar show the progress. The administrator's view of all photos has no events for other users' photos, so it reads its month counts again every 10 seconds while it is in view and loads the months that changed. The trash still lists them | Decided with the user on 2026-11-18. Before processing a photo has no date or size: it showed as a square in the current month and moved to its own month when it was ready, so uploading old photos made the timeline jump with every file. Reading the date and size during the upload would place them at once, at the cost of running exiftool before each upload answers |
| Browser uploads into an album | The upload dialog chooses files or a whole folder, with its subfolders, and has an album field, empty for the library only, which also takes the name of a new album, created once the files are chosen. The album page opens the dialog with itself filled in, and files dropped on it go into it; files dropped on the timeline go into the library only. Folders can be dropped too. Of a folder's files, the browser sends only those whose extension is that of a supported photo or video, so that its `.aae` or JSON files are counted as skipped, and listed on request, rather than refused one by one. Hidden files and folders, such as `.DS_Store` and macOS `._` files, are left out without being counted. `POST /photos?album=` checks that the album is the uploader's own before reading the file and adds the photo, a duplicate included, as a WebDAV album does | Decided with the user on 2026-11-18. The album is a query parameter, as the file streams into ingest and a form field after it would come too late. Choosing the album first, rather than adding photos afterwards, keeps a large upload from being lost in the timeline |
| Upload limits | 512 MiB for a photo and 4 GiB for a video, from the browser and over WebDAV, with no resuming of a failed upload. A folder scan has no limit | The limit is checked after the file type is known, while the upload streams to disk. A folder scan reads files already on the server |
| ffmpeg | ffmpeg and ffprobe built in the image from the release Debian trixie ships, with only what the application uses: the MOV and MP4 demuxer, the H.264, HEVC, VP9, AV1 (dav1d), MPEG-4, ProRes and MJPEG decoders, `zscale` and `tonemap` for HDR, and the PNG encoder. They run as separate processes and take about 11 MB. A new codec or filter means another `--enable` in `deploy/Dockerfile`. The transcoder's image for Intel graphics builds it again with VAAPI, OpenCL, the H.264 VAAPI encoder, AAC and the MP4 muxer for video copies, and its image for AMD graphics the same without OpenCL | Debian's `ffmpeg` package added about 360 MB of libraries the application never loads, taking the arm64 image from 448 MB to 932 MB on disk. A separate service for probing and posters would need the files sent over the network or a shared volume. Video copies, which need drivers, run in the transcoder with shared volumes, as decided on 2026-11-14 |
| RAW photos | Ingest recognizes camera RAW signatures and uses the extension for TIFF-based formats. Previews use the largest embedded JPEG from ExifTool when it reaches the viewer size, then explicit libvips `magickload` through ImageMagick's LibRaw coder, then any embedded JPEG. Stored dimensions follow the upright preview source. RAW + JPEG matches use owner, base name, capture timestamp including sub-seconds, and camera make and model. Processing and the periodic version-linking job both check for pairs. | The camera's JPEG preserves its rendering and usually costs less to process. The viewer always shows a preview and downloads the original. |
| Motion photos | The video embedded in a Google or Samsung motion photo, in JPEG or HEIC, is extracted during processing with `exiftool -b`, from `MotionPhotoVideo` or Samsung's `EmbeddedVideoFile`, and kept next to the previews. Google's older MicroVideo format, from the Pixel 2 and 3 and other phones up to about 2019, only gives the video's length from the end of the file in `MicroVideoOffset`, which exiftool does not extract, so that video is cut from the end of the file. A photo whose tag remains after an editor dropped the video stays a still photo. A Huawei or Honor moving picture carries no tag: the file ends with text fields of 20 bytes, the last of them `LIVE_` and a length, and the video before them is cut to its whole MP4 boxes. It is found by the end of the file during processing, so the `backfill_motion` job does not find such photos processed before. Other photos processed before that get their motion from a `backfill_motion` job, at every start and once a day, which finds them by the tag in their stored EXIF and leaves their previews as they are. The grid marks such photos, and the viewer plays the motion once over the photo by a button | Checked on 2026-11-11 with real files from a Pixel 9 Pro XL and five Samsung models, including a Galaxy S20 with only Samsung's trailer. MicroVideo checked on 2026-11-12 with `MVIMG_` files from Wikimedia Commons, Xiaomi's included. The Huawei trailer checked on 2026-11-12 with a file from a MediaPad M5; the longer trailer of later writers is known only from reverse-engineered writers |
| Live Photos | The photo and the video of an iPhone Live Photo are two files that share Apple's `ContentIdentifier` tag, kept in a generated column from the stored EXIF. Whichever comes second, processing pairs them, and a `pair_live_photos` job, at every start and once a day, pairs the files processed before and any pairing that failed. A pair is one photo and one video of the same owner, the oldest of each when there are more, and neither may be in the trash: a video that came while its photo was there pairs when the photo is restored, from the trash or by an upload. The video is then hidden under its photo by a `live` link in `photo_links`: it is left out of every list, search and count, its own albums, tags and shares included, and is not embedded. The photo plays it as its motion, as a motion photo does, to whoever can see the photo. The video goes into the trash, out of it and away for good only with its photo, and an upload of the video again answers with the photo. Files without the tag are not paired, by name or otherwise. A browser's file picker hands over only the photo of a Live Photo, so the video comes over WebDAV or from an export of the originals | Decided with the user on 2026-11-12; the link moved from a `live_photo_id` column into `photo_links` on 2026-11-17, see Versions. The motion photo's button, mark and address serve the pair unchanged. Pairing by name and time could join files that do not belong together. The video follows its photo, so that WebDAV or a folder scan does not add a purged video back on its own |
| Versions | A file can be hidden under another photo: the video of a Live Photo under its photo (`live`), the original of an edited copy from an import under the copy (`edited`), or a camera RAW under its JPEG (`raw`). `photo_links` keeps one row per hidden file, with the photo it is under and the kind, so a file is under one photo only and a photo has at most one Live Photo video and one RAW. Links may chain, as when the original of an edited copy has its Live Photo video under it. A hidden file is left out of every list and count, goes into the trash, out of it and away for good only with the photo at the top, and an upload of it answers with that photo. Only its owner and administrators open a hidden file by its id; others see it through the shown photo, such as its motion. The edited copy plays the motion of its original. When an original is hidden under its copy, the copy takes over its albums, album covers, direct shares, visibility to all and tags. The owner's viewer offers a switch to the original | Decided with the user on 2026-11-17. A table rather than a column, so that RAW and JPEG pairs and later links such as bursts and duplicates, which need not hide anything, fit in, and a photo can have several versions of different kinds. `kind` is text with a check, as a PostgreSQL enum value cannot be used in the transaction that adds it. The original of an edited copy stays with its owner, as an edit often crops or hides something |
| Descriptions | A photo has one description, `photos.description`, up to 2000 characters with line breaks kept. Everyone who can see the photo sees it in the viewer; only the owner edits it. An import fills it from the description in Google's JSON when the photo has none, so it never replaces the owner's text | Decided with the user on 2026-11-17, as in Google Photos, where a description goes with the shared photo |
| Favorites | `photo_favorites` holds each user's own marks, on any photo the user can see that is not hidden, in the trash or purged; nobody else sees them. The viewer's star and the selection bar set them, and the Favorites page lists the user's own and others' marked photos. A mark moves no `updated_at` and sends no event; the page that changed it updates itself. An import marks what Google had as a favorite for the import's owner, on the photo at the top of its chain, and linking an edited copy moves every user's marks from the original to the copy | Decided with the user on 2026-11-15 and 2026-11-17. List items do not carry the mark, so the lists stay as they are; only `GET /photos/{id}` tells it |
| Archive | `photo_archive` holds each user's own archive, on any photo the user can see that is not hidden, in the trash or purged. An archived photo leaves that user's timeline, its months and facets, also when it is filtered by tag, and stays in albums, favorites, search and the photos shared with the user; the Archive page lists it. Archiving from the timeline or the viewer drops the photo from the open list, as trashing does, and sends no event. Imports and linking treat it as they treat favorites | Decided with the user on 2026-11-15 and 2026-11-17, as Google Photos keeps archived photos in albums and favorites |
| Database backups | A `backup` container on the `postgres:18` image dumps the database every night with `pg_dump` and keeps the latest 14 dumps. Originals are backed up as folder snapshots, such as ZFS snapshots on TrueNAS. Previews are not backed up: the `render-previews` command makes them again from the originals | `pg_dump` always matches the server version, the application image stays as it is, and the setup stays a single YAML on TrueNAS. Previews take hours to remake, but nothing is lost without them |
| Restoring a dump | Restoring moves the photo numbers a million past the dump's | Browsers cache previews for a year by photo number. Photos uploaded after the dump are lost from the database, and a new photo with the number of one of them would show its cached preview |
| Logs | Plain text by default, or JSON, on the container output, at a level set in the environment. Each request is logged, at `info` when it fails or takes over a second and at `debug` otherwise. Docker keeps five files of 10 MB | Errors and slow requests are visible without the noise of every preview |
| Queue metrics | A section of the administration page: jobs by kind and state, finished and failed in the last hour and day, and the latest errors. It updates through server-sent events, with the server reading the queue every 2 seconds and sending only changes | Visible without a monitoring system. SSE as for processing progress. River does not report finished jobs, so the server polls its table |
| ML service | A separate stateless service in Python that turns a viewer preview or a search text into a vector. It has no access to the database: the application calls it, stores the vectors and checks permissions. Its address and a token are set in the environment. It runs on a Mac first, natively with PyTorch on the GPU, and can move to a cloud GPU without recomputing vectors | The service can run anywhere, including outside the home network, with no database credentials. Docker on macOS has no GPU access. The same model weights and preprocessing give the same vectors on any hardware |
| ML availability | The application asks the service for its health every 30 seconds and keeps its state: unavailable, available, or running a model other than the configured one. Embedding runs only while it is available. The interface disables text search while the service is down, and the administration page shows the state, the model and the progress | The test machine is often switched off, and the library must work without it. A different model would mix incomparable vectors |
| Embedding queue | No job per photo. A periodic job on its own queue with one worker takes processed photos that have no vector for the configured model, in batches, and stops when none are left or the service goes away. A photo that fails three times is skipped and listed on the administration page | Per-photo jobs would fail or pile up while the service is off for days. New photos, a first run over the library and a change of model need nothing extra: they all show up as photos without a vector |
| Embedding storage | `pgvector` in the main database, half-precision vectors keyed by photo and model. No FAISS. Search starts with an exact scan, and an HNSW index per model is added only if it gets slow. The database runs on `pgvector/pgvector:pg18-trixie`, and the `backup` container stays on `postgres:18` | The permission predicate and the vector search run in one query. Filtering FAISS results afterwards would leave a user who sees a small part of the library with few or no results. A home library is small enough for an exact scan. The `trixie` image is built on the same Debian release as `postgres:18`, so an existing database keeps its collations; the plain `pg18` tag is an older release with an older glibc |
| Interface language | English, Russian, Simplified Chinese, Spanish, Brazilian Portuguese, German, French, Japanese, Korean and Italian, with vue-i18n and the messages in TypeScript files, one per language. Chinese, Japanese and Korean use the system's fonts. Each user chooses the language in the profile. The default is automatic: the browser's language, or English when the application does not support it. The choice is stored with the user. Dates, numbers, Vuetify's own texts and place names follow the chosen language. The API keeps its errors in English, and the interface shows its own text for the ones it knows | The users of one library may prefer different languages. The browser's language is the best guess before a user chooses. vue-i18n is the usual choice for Vue, takes plural rules per language (built on `Intl.PluralRules`), and Vuetify has an adapter for it. TypeScript messages let the type check catch a missing translation or a mistyped key |
| Place names (planned) | The viewer shows the name of the place in place of the coordinates, linked to the map as the coordinates are now. The names come from the GeoNames `cities1000` dump (CC BY 4.0) in a database table: processing finds the populated place nearest to the photo's location, and a periodic job does the same for photos processed before. The photo keeps the place's identifier, and the name is shown in the interface language, or in English when GeoNames has no name in it. A place name is location data: the API returns it only when an administrator allows locations, and the viewer hides it with the location | Coordinates never leave the NAS, and no internet is needed. The public Nominatim would receive the location of every photo, allows one request per second and discourages bulk lookups. A self-hosted Nominatim or Photon needs gigabytes of map data. The cost is accuracy: the name is of a town or village, not a street, and outside towns the nearest village can be a few kilometres away |
| TLS and HTTP/2 | Caddy in front of the application | The grid loads hundreds of previews, and HTTP/1.1 allows few connections. WebDAV Basic Auth requires TLS |

The main hardware constraints are CPU time for decoding photos and, probably, HDD throughput. Memory is not scarce.

## Ingest and processing

All sources (browser, folder scan, WebDAV) go through a single `Ingest(file, owner)` path:

1. Stream the file to a temporary file on the same filesystem, computing SHA-256 along the way.
2. Check for duplicates with `UNIQUE (owner_id, sha256)`. Deduplication is per user only.
3. Atomically rename the file to `originals/{owner_id}/{sha[:2]}/{sha}.{ext}`. Originals are never modified.
4. In one transaction, create the photo record and a `process_photo` River job.
5. A worker reads EXIF, applies auto-rotation and sRGB conversion, generates a grid preview (400 px on the shortest side) and a viewer preview (2048 px on the longest side) on the SSD. Until a preview loads, the grid shows a neutral tile. Previews are WebP: in the [benchmark](benchmark.md#results) they take about 45% less disk space than JPEG, and the slower encoding is a one-time background cost. The format, quality and sizes can be changed on the administration page, and apply to new photos. AVIF is ruled out because of its encoding cost. A video gets its previews from its poster frame, and a motion photo also gets its embedded video extracted, as described under Videos and Motion photos above.
6. A periodic job removes abandoned uploads and expired sessions. It leaves originals without a database record alone: after restoring an older database backup, those are the photos uploaded since that backup. A stray original is harmless, and uploading the same photo again reuses it.
7. Permanently deleting a photo from the trash removes its original and previews, and leaves a record with only its hash. A database lock on the owner and hash keeps this from colliding with an upload of the same file.

A folder scan lists the files in the chosen folder with their sizes and modification times, waits, and passes each file to ingest if neither has changed. It hashes a file before copying it, so a repeat scan reads everything but writes only what is new. Duplicates in the trash stay there, unlike with an upload. It leaves out the `.aae` edits of Apple Photos and the `.supplemental-metadata.json` files of Google Takeout without a report.

A Takeout scan is the other kind of folder scan, chosen in the same form. It reads the Google Takeout exports in the folder: their `.zip`, `.tgz` and `.tar.gz` parts, without unpacking them, and unpacked `Takeout` folders; other files are left out. Parts are grouped into exports by the time in their names, and every file read is kept in `takeout_entries` with its export, its path, the part it came from and its photo, duplicates included, and every JSON file with its content, for the steps of [improvement 10](improvements.md#10-import-from-google-takeout-and-icloud) that follow. After the matching, every album of the exports, a folder right under the product folder with a JSON file whose `title` is a string, fills the owner's album of that name, the oldest if there are several, or a new one, so an album imported again or found in several exports stays one album; the description and Google's sharing of the album are not used. Photos of the folder are added, and the scan form says what happens to those in the owner's trash: they are left out, added, or added and restored. At the end, after the albums, the photos the scan added to the library whose newest JSON says Google had them in the trash go to the trash, dated when the scan started; a photo the library had before is never moved to the trash by an import. A `.zip` entry is hashed before it is copied, as a file of a folder is; a `.tgz` part can only be read in order, so its entries are copied to a temporary file first, and a pause in the middle reads the part again from its start, skipping what is done.

WebDAV serves each user's tree at `/webdav/`. `x/net/webdav` handles listings, folders, moves, deletes and locks over the tree in the database. Uploads and downloads bypass it: a PUT streams the file into ingest, which treats the trash as a folder scan does, and records the file with its size and the modification time the client sends in `X-OC-Mtime`. If the file's folder, or a folder above it, is linked to an album, the photo is added to the album of the nearest one before the file is recorded, so that a failure makes the client send the file again. The server logs every WebDAV request with its client, to see how sync apps behave.

Queue behavior:

- 3 workers, leaving one core for the UI
- Bulk imports run at low priority
- Processing resumes where it stopped after a restart

## Machine learning

The ML service has three endpoints: `GET /health` returns the model, the vector size and the preprocessing version; `POST /embed/image` takes a batch of viewer previews; `POST /embed/text` takes a search text. The model name stored with a vector includes the preprocessing version, as resizing and normalization happen in the service.

- **Embedding:** while the service is available, a periodic job on the `ml` queue selects processed photos without a vector for the configured model, sends their viewer previews in batches and writes the vectors. It starts every minute and as soon as the service becomes available.
- **Text search:** a page of its own. The application gets the vector of the text from the service, then sorts the photos the user can see by their distance to it and leaves out those below the model's similarity threshold, which the service gives with the vector. Without the threshold a query with no match would still return the nearest photos. Results are ordered by relevance, not by date, so they do not fit the timeline with its months.
- **Similar photos:** the application takes the photo's vector from the database and finds the nearest ones the user can see, with no threshold. This needs no ML service.
- **Deleting:** the permission predicate hides photos in the trash, and permanently deleting a photo removes its vectors with its previews.

## Data model

- `users` (login, argon2id password hash, admin/user role, disabled flag, whether "Shared with me" includes album photos, whether zooming in the viewer loads originals, which photo details it hides, whether the menu hides on a phone, whether the grid shows squares and the size of its tiles, whether the timeline includes shared photos), `sessions`
- `photos` (`bigint` id, owner, SHA-256, MIME type, size, dimensions, `taken_at`, EXIF as JSONB, the camera and lens generated from it, status, preview format and version, private/all visibility, `deleted_at`, `purged_at`, the duration of a video, whether a motion photo or a Live Photo has its video, the `ContentIdentifier` of a Live Photo and, on its video, the photo it belongs to, and the state of the H.264 copy of what it plays). Videos are rows of this table, told apart by a `video/` MIME type.
- `photo_shares`, `albums` (with private/all visibility), `album_photos`, `album_shares`
- `tags` (owner, name), `photo_tags`
- `preview_settings` (one row: format, quality and preview sizes), `metadata_settings` (one row: whether the API returns locations), `video_settings` (one row: when H.264 copies of videos are made)
- `app_passwords` (user, device name, SHA-256 of the password, last use), `webdav_entries` (user, path, folder or file, size, modification time, the photo), `webdav_albums` (user, folder path, album)
- `photo_embeddings` (photo, model, vector), `photo_embedding_failures` (photo, model, attempts, the last error)
- `import_runs` (scan report: found, added, duplicates, in the trash, permanently deleted, unsupported, still changing, failed), `import_files` (files still to process, and the ones to report)

## Access control

Permissions are checked in one place: a single SQL predicate, "this photo is visible to this user", used by every query, including file delivery. A photo is visible if any of these is true:

- The user is an admin or the photo's owner
- The photo is visible to all users
- The photo, or an album containing it, is shared with the user or visible to all users

A photo in the trash is visible only to its owner. Its sharing comes back when it is restored.

Authentication uses sessions in HttpOnly cookies. There is no registration: the first admin is created with a CLI command, and the admin manages all other users.

Previews contain no EXIF. The API returns only the camera details: camera, lens, focal length, aperture, shutter speed, ISO, exposure compensation and flash. It returns the GPS location only if an administrator turns it on, and then to everyone who can see the photo. Originals keep all EXIF, including GPS data, and recipients can download them. The share dialog warns about this.

Revoking access takes effect on the server at once. Previews are cached for a year as private, so a browser that already loaded one can still show it from its cache.
